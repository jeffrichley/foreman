## Goal

Refactor the v3 reconciler's hand-authored rule catalog (`packages/foreman/src/foreman/reconciler/rules.py`, currently ~650 lines including predicate helpers) into a **derived** catalog generated from declarative role contracts. Each role + transition gets one source-of-truth declaration; the dispatch / advance / budget / safety rule entries are produced by a derivation function. The migration must preserve the existing catalog rule-for-rule via a keystone equivalence test, and must preserve the "GitHub-is-truth, per-ticket independent, operator-overridable via labels" semantics that `rules.py` enforces today. See [#160](https://github.com/jeffrichley/foreman/issues/160).

This is a v4 architectural change with no urgent fire driving it. The win is structural: the bug shape behind #151, #156, and #158 was "predicate prose drifted from the dispatch contract"; making the contract the source and the predicate the derivation collapses that drift surface.

## Acceptance criteria

- New module `packages/foreman/src/foreman/reconciler/role_contracts.py` exists. It declares a frozen dataclass (or equivalent typed structure) `RoleContract` capturing the per-role attributes the rule derivation needs. The minimum set of fields is:
  - `name: str` — the rule-catalog name prefix used today (e.g. `"dispatch_planner"`, `"dispatch_reviewer_spec"`).
  - `action: Action` — the `foreman.reconciler.actions.Action` enum value the dispatch rule fires.
  - `entry_labels: frozenset[str]` — the issue labels that gate dispatch (e.g. `{"foreman:planning"}` for Planner, `{"foreman:impl-fix"}` for FixerImpl).
  - `pr_shape: Literal["spec", "impl", "none"]` — branch shape the rule's PR-existence checks demand; `"none"` for rules that fire pre-PR (Planner).
  - `action_key: str` — the `execution_log.action` string the predicate uses for `count_completed` / `has_unterminated`. Equals `action.value` today for every existing role; keeping it explicit decouples the contract from the enum string.
  - `retry_budget: int | None` — the per-cycle attempt cap. `None` for rules with no budget (today: idempotence-only gates like `_planning_no_pr`'s success-count==0).
  - `idempotence_gate: Literal["success_only", "any_terminal", "no_count_gate"]` — selects which of the three counting modes the predicate uses today (see `_planning_no_pr` for `success_only`, `_planning_pr_needs_review` for `any_terminal` with budget cap, `_attempt_merge_plan_eligible` for `no_count_gate`).
  - `dispatch_invocation: DispatchInvocation` — the structured form that `V3GitHubHost.dispatch_role` consumes today via its own switch (role, target, whether it accepts `--pr-url`, whether it uses positional issue/PR URL). Required for the v3_host wrapper change in sub-request 4.
- New module `packages/foreman/src/foreman/reconciler/derivation.py` exists. It exports `derive_rules(contracts: Sequence[RoleContract], safety: Sequence[Rule]) -> tuple[Rule, ...]` which:
  - Returns `safety` rules verbatim followed by one forward-progress dispatch rule per contract.
  - Generates a budget safety rule for every contract whose `retry_budget` is set, with predicates equivalent to `_fix_attempts_exhausted` / `_impl_attempts_exhausted` / etc.
  - Generates the head-ref filter from `pr_shape` (today: `head_ref.startswith("foreman/issue-")` for spec, `head_ref.startswith("foreman/impl-")` for impl, no filter for `"none"`).
  - Generates the `has_unterminated` + `count_completed` predicate arm from `action_key` + `idempotence_gate`.
  - Wraps every safety predicate it generates in `_safety_with_rate_limit` (today's wrapping behavior in `rules.py:148-219`).
  - Preserves precedence values: the derived catalog's `Rule.precedence` values must equal the hand-authored catalog's values **for the same `Rule.name`**, so the existing precedence-invariant tests (`test_rules_precedence.py`) continue to pass unchanged.
- New keystone test `packages/foreman/tests/reconciler/test_rules_derivation_equivalence.py` exists. It builds the derived catalog from the role-contract declarations + the unchanged safety predicates, then asserts:
  - **Set equality on rule names.** The derived catalog has the same set of `Rule.name` values as today's `RULES`.
  - **Per-rule attribute equality.** For each shared `name`, the derived rule's `tier`, `precedence`, and `then` match `RULES`.
  - **Behavioral equivalence.** For a parameterized matrix of `ActionContext` fixtures covering the existing 13 rule paths (built from the fixtures already used in `test_rules.py`), `evaluate(ctx, rules=derived)` produces the same `(Action, rule_name)` pair as `evaluate_with_rule(ctx, rules=RULES)`. The matrix must include at minimum: (a) every label transition exercised by the current `test_rules.py`, (b) the head-ref filter cases (spec PR + impl label, impl PR + spec label), (c) every safety-budget exhaustion case, (d) the lagging-label rules.
- The keystone test fails if a rule is dropped, renamed, or has its predicate semantics changed by the derivation. It is the migration's safety gate.
- The hand-authored RULES tuple in `rules.py` is **deleted** in this PR's final commit, replaced by `RULES = derive_rules(_ROLE_CONTRACTS, _SAFETY_RULES)`. `_SAFETY_RULES` remains hand-authored — the open-question section explains why (operator-control labels and CI-failure rules don't fit the role-contract abstraction).
- `V3GitHubHost.dispatch_role` (`packages/foreman/src/foreman/reconciler/v3_host.py:716-858`) is refactored to consume `DispatchInvocation` from the contract instead of the role-name `if/elif` chain at `v3_host.py:780-811`. The existing `_ROLE_TO_SUBCOMMAND` map and the per-role argv assembly are replaced by reading the structured invocation off the contract for the dispatched action. The role-name → subcommand mapping (today's lookup at line 773) becomes a field on `RoleContract`.
- `_DISPATCH_ROLE_FOR_ACTION` in `actions.py:106-113` is reduced to a function that walks `_ROLE_CONTRACTS` and finds the contract whose `action` matches. The dict literal goes away; `execute_action`'s branch at `actions.py:345-353` consumes the new lookup.
- Every existing test in `packages/foreman/tests/reconciler/` (notably the 1157-line `test_rules.py`, 840-line `test_actions.py`, 1401-line `test_v3_host.py`) continues to pass without semantic changes. Test signature updates are allowed only where they ride along the type change of `_DISPATCH_ROLE_FOR_ACTION`.
- `just check` passes (lint + typecheck + tests).

## Approach

The current `rules.py` codifies four repeating patterns per role:

1. **Dispatch rule:** `entry_label ∈ labels ∧ PR-shape predicate ∧ ¬has_unterminated(action_key) ∧ count_completed(action_key) < budget → dispatch`.
2. **Advance rule:** specific label transitions on terminal states (e.g., `spec_pr_merged_label_lagging → ADVANCE_LABEL_TO_PLAN_APPROVED`).
3. **Budget safety rule:** `entry_label ∈ labels ∧ count_completed(action_key) ≥ budget → surface_help`, wrapped in `_safety_with_rate_limit`.
4. **Operator-control safety rule:** `foreman:hold` blocks all; `foreman:needs-help` surfaces; conflict / CI-failure rules.

Of the four, patterns 1 and 3 are mechanical and 1:1 with a per-role configuration record. Pattern 2 (label transitions) is partly mechanical and partly bespoke (the merging-plan / merging-impl / lagging-label rules have distinct shapes). Pattern 4 is policy that does not key off any role; today's `_SAFETY_RULES` tuple is the right shape for it.

The refactor's discipline is to **derive what is mechanical (1 + 3) from a `RoleContract` declaration; keep what is bespoke (parts of 2 + all of 4) hand-authored**. The keystone equivalence test is the gate that proves no behavior changed.

The shape mirrors existing patterns already in the codebase:
- `actions.py:106-113` already has a `_DISPATCH_ROLE_FOR_ACTION` mapping that the executor consults to find the role + target for a `DISPATCH_*` action. This is a table-driven dispatch — the refactor extends it from a flat mapping to a richer typed structure (`RoleContract`) and uses the same structure to drive rule generation.
- `v3_host.py:780-811`'s `if role == "reviewer" / elif role in ("planner", "worker") / elif role == "fixer"` cascade is exactly the kind of per-role argv assembly the contract should own. After the refactor, `dispatch_role` reads the structured `DispatchInvocation` and assembles argv from it, without conditional branching on role identity.
- The existing precedence convention (safety < 100, forward-progress ≥ 100; tested in `test_rules_precedence.py`) is preserved by encoding the precedence value on each `RoleContract` directly, not by computing it from contract order. Computing precedences would invalidate the precedence-invariant tests and risk silent reordering — explicit values, identical to today's, is the safer migration.

The `idempotence_gate` field is intentionally a small enum, not a free-form predicate, because today every dispatch rule uses one of exactly three counting modes (see acceptance criteria for the three values). Generalizing further would over-engineer the abstraction — when a future rule needs a fourth mode, add the enum case then.

The keystone test deserves its own paragraph. It is not a unit test for the derivation function; it is a behavioral diff between the hand-authored catalog (the proven-in-production source) and the derived one (the proposed source). It runs every fixture from `test_rules.py` against both catalogs and asserts the `(Action, rule_name)` outputs match. Until this test passes for every fixture, the migration is incomplete; once it passes, deleting the hand-authored RULES is safe. After the migration, the keystone test stays as a regression guard — if a future change to the derivation drops or renames a rule, the test fires.

## Alternatives considered

- **Full state-machine library (XState / pytransitions / Akka FSM).** Rejected. Pulls in a third-party dependency the daemon doesn't otherwise need, and forces a reshape of the existing predicate-over-`ActionContext` model into a node-and-transition graph. The win this issue describes — collapsing the per-role boilerplate — is achievable without a state-machine library; the underlying evaluation model (linear precedence-ordered rule scan) is already fine. The library would introduce a new abstraction layer to learn for a problem this codebase has already solved.
- **Build the role-contract abstraction without deleting hand-authored RULES (add derivation as a parallel path).** Rejected. The whole point of the refactor is to make the contract the single source of truth; leaving the hand-authored catalog beside the derived one re-creates the drift surface the issue is trying to remove. The keystone equivalence test is sufficient safety for the cutover — once it passes against the unchanged `rules.py`, deleting the hand-authored entries is safe. Long-lived parallel paths are technical debt.
- **Generalize `idempotence_gate` to a callable instead of a small enum.** Rejected for v4. Every dispatch rule today uses one of exactly three counting modes; making the gate a callable opens a back-door for future rules to encode arbitrary predicate logic on the contract, which re-creates the hand-authoring problem the refactor is trying to solve. If a future rule genuinely needs a fourth mode, adding an enum case is one line and forces the contract to declare it explicitly. (See: the `Literal` types this codebase already uses for `target` and `pr_shape` — small enums are the consistent shape.)
- **Treat advance/merge actions (ADVANCE_LABEL_TO_*, ATTEMPT_MERGE_*) as role contracts too.** Rejected for this PR. See "Open questions" — these actions have a different lifecycle (synchronous label change, not subprocess spawn) and don't share enough structure with role dispatches to fit a unified contract. Forcing them in would require a `RoleContract` with optional fields the dispatch path ignores, which is a worse abstraction than two clean abstractions. Revisit in a follow-up after the role-contract derivation has been in production for one full cycle.

## Open questions

- **Should `ADVANCE_LABEL_TO_*` and `ATTEMPT_MERGE_*` actions get their own derivation?** The issue raises this. Today's rules `advance_label_to_merging_plan`, `attempt_merge_plan`, `advance_label_to_plan_approved_lagging`, etc., are label-state transitions, not subprocess spawns. They share structure with each other (label-set predicate → label-set transition) but very little with dispatch rules (subprocess spawn with argv assembly + concurrency cap + termination tracker). This spec scopes the derivation to dispatch + budget rules only, leaves the label-transition rules hand-authored, and proposes the unified abstraction as out-of-scope follow-up work after the dispatch-side derivation has shaken out in production for at least one full Planner → Worker → Reviewer → merge cycle. If the Reviewer judges the unified abstraction should land in this PR instead, the scope adjustment is small but real (one more dataclass + ~5 more derivation cases + ~30 more keystone fixtures).
- **Should `_SAFETY_RULES`' CI-failure rules (`impl_pr_ci_failure`, `spec_pr_ci_failure`, `mergeable_conflict`) be derived from `pr_shape` in some way?** Today they encode head-ref filters that look mechanical, but the bound triggers (CI status, conflicting mergeability) are not "the role's input contract" — they're operator-grade safety signals. Leaving them hand-authored is the conservative call for v4; mention the question because they could plausibly be folded in.
- **Does `RoleContract` need a serialization story (TOML, JSON-schema export) for documentation / config?** Out of scope for this PR; flagged because the issue mentions "testable in isolation" and serialization would make role contracts grep-able + diff-able across versions for a future change-management process. Defer to a separate ticket if the team wants it.

Confidence: medium. The mechanical part (dispatch + budget rule derivation) is well-understood from reading the existing predicates side-by-side; the keystone equivalence test gives a hard safety gate for the cutover. The genuine uncertainty is the scope boundary around advance / merge actions, captured as the first open question above.

## Out of scope

- Refactoring the safety-tier CI-failure rules (`impl_pr_ci_failure`, `spec_pr_ci_failure`, `mergeable_conflict`) or operator-control rules (`hold_label_blocks`, `needs_help_label`) into the derivation. They stay hand-authored in `_SAFETY_RULES`.
- Refactoring the label-transition rules (`advance_label_to_planning`, `advance_label_to_merging_plan`, `attempt_merge_plan`, `advance_label_to_plan_approved_lagging`, `advance_label_to_merging_impl`, `attempt_merge_impl`, `advance_label_to_done`) into the derivation. They stay hand-authored in a new `_LABEL_TRANSITION_RULES` tuple inside `rules.py`. The "transition action" abstraction the issue mentions is deferred to a follow-up.
- Changes to `ExecutionLog` schema, action enum values, or any GraphQL query. The derivation reads from the existing `ExecutionLog` API (`count_completed`, `has_unterminated`, `has_recent`) and emits today's `Action` enum values unchanged.
- Re-numbering or re-ordering rule precedences. The derived catalog must reproduce today's precedence values exactly so `test_rules_precedence.py` continues to pass without modification.
- Threading per-role contracts through `cli.py`, `daemon_runners.py`, or the role implementations themselves. The contract data lives in the reconciler package and is consumed by the reconciler + the dispatch host; the role binaries (planner, reviewer, fixer, worker) continue to read their inputs from CLI argv as today.
- Removing any safety rule, even a redundant one. The keystone equivalence test would fail; that is by design.
