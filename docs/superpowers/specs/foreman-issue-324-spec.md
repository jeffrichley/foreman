# Spec: opt-out impl-merge — close the issue + add `foreman:awaiting-operator-merge` (issue #324)

## Goal

The issue body asks for an opt-in impl-PR auto-merge flag on a "v4" architecture (`packages/foreman/src/foreman/v4/...`, `MergingState`, `observers/label_observability.py`). That v4 architecture does NOT exist in the repo; the active path is the v3 reconciler at `packages/foreman/src/foreman/reconciler/`. The v3 reconciler **already implements the opt-in default** the issue describes — `ReconcilerConfig.auto_merge_impl: bool = False` (`config.py:237-245`) is the global default, `ProjectConfig.auto_merge_impl: bool | None = None` (`config.py:498-506`) is the per-project override, and `_advance_label_to_merging_impl_when_eligible` (`reconciler/rules.py:553-573`) gates the merge action on the effective flag.

Two **real gaps** remain between today's v3 behavior and the issue's stated semantic intent, and this spec ships those gaps:

1. **The GitHub issue is not closed when an impl PR is observed merged externally** (the opt-out path). The v3 reconciler advances `foreman:impl-approved` → `foreman:done` via `_impl_pr_merged_label_lagging` (`reconciler/rules.py:592-605`) + `ADVANCE_LABEL_TO_DONE` (`reconciler/actions.py:89, 806-818`), but only updates labels — it never calls `host.close_issue`. The v2 `DaemonRunners.merge_impl_pr` (`daemon_runners.py:209-255`) closes the issue, but only fires when foreman auto-merges. So when `auto_merge_impl=False` and the operator merges externally, the ticket reaches `foreman:done` while the GitHub issue stays open — that is the loop's close-out gate from foreman#63 leaking.
2. **Operators have no glanceable surface to find tickets parked in the opt-out wait state.** When `auto_merge_impl=False`, the ticket sits at `foreman:impl-approved` indefinitely. From an operator's label-filter view, that is indistinguishable from a normal mid-pipeline impl-approved ticket where the merge attempt has just not happened yet.

This spec ships (1) a `close_issue` capability on the v3 `ReconcilerHost` protocol + a call from the `ADVANCE_LABEL_TO_DONE` executor branch, and (2) a new `Label.AWAITING_OPERATOR_MERGE` / `foreman:awaiting-operator-merge` label + a new rule `advance_label_to_awaiting_operator_merge` that stamps it when the ticket reaches `impl-approved` under `auto_merge_impl=False`. See issue [#324](https://github.com/jeffrichley/foreman/issues/324). Adjacent prior art: foreman#165 (v3 state-machine-driven merge phase), foreman#279 / foreman#294 (impl-PR base retarget), foreman#63 (issue-closure routing must go through the daemon, not PR-body auto-close).

## Approach

Per `CLAUDE.md`'s Decision-4 calibrated lens, this change reads cleanest under Google's **"make the right thing easy"** principle, not under a single GoF pattern. The behavioral state machine that drives the close-out gate already exists (the v3 reconciler's rule catalog and action executor); what's missing is a small set of well-placed transitions and one host capability that makes the externally-merged path land cleanly without operator follow-up. The wait-label addition is a State-pattern-adjacent move — the label IS the state, and the new rule is one more transition into that state — but State qua pattern doesn't materially fit here because the existing reconciler is rules-over-data, not objects-over-states. **No GoF pattern fits cleanly; this is straightforward state-machine completion plus one new protocol method**.

The honest framing of the issue: it was authored against an imagined "v4" architecture (`MergingState.execute`, `observers/label_observability.py`, etc.) that does not exist in this repo. The semantic intent — opt-in default for impl-merge, with operator-visible park state and clean close-out on observed merge — is sound, and the v3 reconciler already implements 80% of it. The 20% delta is the two real gaps above. This spec ships ONLY those gaps; everything else the issue describes (`ProjectConfig.auto_merge_impl: bool = False`, threading the field through MergingState, etc.) is either already correct or vocabulary-mismatch.

The `close_issue` addition to `ReconcilerHost` (item 1) is the load-bearing move. The v3 reconciler's `_impl_pr_merged_label_lagging` rule (`rules.py:592-605`) already fires when an impl PR is observed merged regardless of who merged it — but the action it dispatches (`ADVANCE_LABEL_TO_DONE`) only stamps the `foreman:done` label. In the autonomous-merge path this works out by accident: the v2 `DaemonRunners.merge_impl_pr` (`daemon_runners.py:209-255`) ALSO fires when foreman merges, and IT calls `close_issue`. In the opt-out path, only the v3 path runs (foreman never calls `merge_pr`), so the issue stays open. The fix is to make `ADVANCE_LABEL_TO_DONE` close the issue itself, which makes both paths symmetric and ends the dependence-on-coincidence. The v2 `daemon_runners` close-out call site (already idempotent — GitHub `issue.edit(state="closed")` is a no-op on already-closed) can stay as defense in depth.

The new `foreman:awaiting-operator-merge` label (item 2) follows the existing labels architecture — `Label` StrEnum + `_FOREMAN_LABELS` catalog + `LabelClass.QUEUE` classification. Why QUEUE and not a new class: the ticket IS queued for the operator's action (their merge button click). Adding a new class would be ceremony — QUEUE membership is what the next-action layer reads, and "next action" in the opt-out path is the operator's merge, conceptually adjacent to "next action: dispatch Worker" in QUEUE-as-it-stands. Precedence 156 for the new rule slots between `dispatch_fixer_impl` (150) and `advance_label_to_merging_impl` (158) so a pending impl-fix still wins (the fix is more important than the wait label) and the autonomous merge path (158 + 162) is never shadowed when `auto_merge_impl=True`.

Observer filter expansion (the `observer.py:55-60` filterBy list) is the easy-to-miss correctness step: without it, once the wait label lands, the ticket falls out of the observer's GraphQL window and the cleanup transition on observed-merge never fires. Adding `"foreman:awaiting-operator-merge"` to the filterBy keeps the ticket visible until the impl PR's merged-state flips True.

The dogfood-config edit the issue asks for (set `auto_merge_impl = true` on `algokit` and `agent_core`) is REJECTED in scope because (a) no `algokit` project exists in the repo's dogfood config (`docker/foreman/config.toml.container`), (b) the existing `agent_core` block does not set `auto_merge_impl`, meaning it inherits the global `False` default already — so the existing dogfood semantic for `agent_core` is opt-out, not opt-in. The issue's "preserve existing autonomous semantics" framing is mistaken on its facts. This is a separate operational decision orthogonal to the close-out-gate fix; if the operator wants to flip dogfood projects to opt-in autonomous merge, that's a one-line TOML edit on a follow-up.

## Alternatives considered

- **Implement the issue body literally as written (v4 architecture, `MergingState.execute`, `LabelObservabilityObserver`).** Rejected because the v4 architecture does not exist in this repo — there is no `packages/foreman/src/foreman/v4/` directory, no `MergingState` class, no `observers/label_observability.py` module. Implementing against an imagined architecture would require building all of v4 first, which is vastly out of scope for one ticket. The v3 reconciler is the active path and already implements 80% of what the issue actually wants; shipping the remaining 20% delta against v3 is the honest move.
- **Change `ProjectConfig.auto_merge_impl` from `bool | None = None` to `bool = False` as the issue body literally states.** Rejected because the existing `bool | None = None` shape is strictly better: it gives `None` semantic ("inherit from global default"), which lets the global default (`ReconcilerConfig.auto_merge_impl: bool = False`) flow through to projects that don't override it. The proposed `bool = False` shape would force every project to set the field explicitly to inherit the global default — a regression. The existing shape ALREADY makes False the effective default for unconfigured projects.
- **Add a separate `LabelClass.WAITING` classification for `foreman:awaiting-operator-merge`.** Rejected as ceremony — the ticket IS queued for the operator's action (their merge), so QUEUE membership is conceptually correct. Adding a new class would require auditing every consumer of `LabelClass` (next-action layer, observer filter, rate-limit checks) to decide how each treats the new class — extensive surface change for no operational benefit. QUEUE classification preserves the existing reads.
- **Set `auto_merge_impl = true` on dogfood configs (`agent_core`, `algokit`) per the issue's AC.** Rejected per Out of scope. (a) No `algokit` project exists in the dogfood config so the criterion is unsatisfiable for it. (b) `agent_core`'s existing config has no `auto_merge_impl` flag, so it inherits the global `False` default — the issue's claim that the existing dogfood semantic is autonomous-by-default is factually wrong. (c) Whether the operator wants the dogfood projects to autonomously merge is an operational decision orthogonal to the close-out-gate fix this spec ships.
- **Put the `close_issue` call inside a separate new action `CLOSE_ISSUE`** instead of extending `ADVANCE_LABEL_TO_DONE`. Tempting because single-responsibility, but rejected because `ADVANCE_LABEL_TO_DONE` already does multi-step label mutation (add `foreman:done`, remove `foreman:impl-approved`) and the issue close-out is conceptually the same transition as labels-to-done. Adding a separate action would require a new rule (`close_issue_when_done`) that gates on the `foreman:done` label, plus an idempotence gate, plus tests — adjacent ceremony for the same outcome. The independent try-wrap discipline (each of the 4 steps independently try-wrapped) gives the partial-failure recovery the separate-action shape would provide.
- **Make the wait label the default park state for ALL impl-approved tickets (regardless of `auto_merge_impl`).** Rejected because the autonomous merge path (`auto_merge_impl=True`) is a short transient state — `impl-approved` → `merging-impl` happens on the same tick or the next. Stamping a `awaiting-operator-merge` label that lives for at most one tick adds churn to the issue's label history with no operator-visible benefit. The label is meaningful precisely BECAUSE it signals the indefinite-park state of the opt-out path.
