# Spec: inject issue comments (and labels) into spec-side role prompts (issue #328)

## Goal
Plumb the originating issue's **comments** (oldest-first, foreman role-bot self-comments excluded) into the user prompts of the three spec-side roles — Planner, Reviewer-on-spec, Fixer-on-spec — and additionally inject the issue's **labels** into the Planner's prompt only. Impl-side roles (Worker, Reviewer-on-impl, Fixer-on-impl) MUST stay byte-identical to their current behavior, even when the issue has comments and labels. Tracks foreman#328.

## Acceptance criteria
- [ ] A `CommentRef` frozen dataclass with fields `author_login: str`, `posted_at: datetime`, `body: str` is exported from `packages/foreman/src/foreman/git_host.py` (sibling to the existing `IssueRef`).
- [ ] `GitHostProvider.get_issue_comments(repo_slug: str, issue_number: int) -> list[CommentRef]` is defined as an abstract method on `GitHostProvider` (`packages/foreman/src/foreman/git_host.py`) and implemented on `GitHubProvider` (`packages/foreman/src/foreman/git_hosts/github.py`). Returns the issue's comments in chronological order (oldest first) with NO filtering applied at the provider layer.
- [ ] A new module `packages/foreman/src/foreman/roles/_prompt_helpers.py` exports:
  - `format_comments_section(comments: list[CommentRef]) -> str` — returns `""` for empty input; otherwise returns `## Comments\n\n### @{login} ({iso8601})\n{body}\n\n` blocks joined and terminated with `\n` so the caller can concatenate directly.
  - `format_labels_section(labels: set[str]) -> str` — returns `""` for empty input; otherwise returns `## Labels\n{label1}, {label2}\n\n` with labels sorted alphabetically for determinism.
  - `filter_bot_self_comments(comments: list[CommentRef], exclude_logins: set[str]) -> list[CommentRef]` — drops any `CommentRef` whose `author_login` is in `exclude_logins`; preserves chronological order.
- [ ] `IdentityRegistry.get_role_bot_logins() -> set[str]` (new method on `packages/foreman/src/foreman/identity.py`) returns the four `f"{slug}[bot]"` strings derived from each role's cached `AppMetadata`. Triggers `_get_app_metadata("planner" | "reviewer" | "fixer" | "worker")` once each on first call; results cached for the registry's lifetime.
- [ ] Planner `_build_user_prompt` accepts new keyword-only params `comments: list[CommentRef]` and `labels: set[str]`. The composed prompt emits `## Comments` and `## Labels` sections between the `## Body` section and the closing "Follow the steps in your system prompt" line, in that order. Both sections absent (no header) when their input is empty.
- [ ] Planner `run_planner` calls `host.get_issue_comments(actual_repo_slug, issue_number)`, then `filter_bot_self_comments(comments, registry.get_role_bot_logins())`, then passes the filtered list plus `set(issue.labels)` into `_build_user_prompt`.
- [ ] Reviewer `_build_user_prompt` accepts a new keyword-only param `comments: list[CommentRef]`. The composed prompt emits a `## Comments` section between `## PR body` and `## Spec doc` when the list is non-empty; absent when empty. NO `## Labels` section.
- [ ] Reviewer `run_reviewer` fetches comments and filters them ONLY when `target == "spec_pr"`. For `target == "impl_pr"` it passes `[]` directly to `_build_user_prompt`, never calling `issue.get_comments()`.
- [ ] Fixer `_build_user_prompt` accepts a new keyword-only param `comments: list[CommentRef]`. The composed prompt emits a `## Comments` section between `## PR body` and the `## Spec doc` block when non-empty; absent when empty. NO `## Labels` section.
- [ ] Fixer `run_fixer` fetches comments and filters them ONLY when `target == "spec_pr"`. For `target == "impl_pr"` it passes `[]` directly to `_build_user_prompt`, never calling `issue.get_comments()`.
- [ ] Worker `roles/worker.py` is UNCHANGED.
- [ ] Unit tests in a new file `packages/foreman/tests/test_roles_prompt_helpers.py` exercise `format_comments_section` (empty list → `""`; two comments → expected literal string with both blocks), `format_labels_section` (empty → `""`; two labels → sorted joined), and `filter_bot_self_comments` (drops matching login, preserves order, returns new list).
- [ ] A new test in `packages/foreman/tests/test_roles_planner.py` seeds an issue with two comments (one from `foreman-planner[bot]`, one from a human `alice`) plus labels `{"foreman:planning", "priority:high"}`, runs `run_planner`, and asserts the resulting `user_prompt` contains `### @alice` and NOT `### @foreman-planner[bot]`, AND contains `## Labels\nforeman:planning, priority:high`.
- [ ] A new test in `packages/foreman/tests/test_roles_planner.py` seeds an issue with two comments at different timestamps and asserts the older comment appears before the newer one in the rendered `## Comments` section.
- [ ] A new test in `packages/foreman/tests/test_roles_planner.py` seeds an issue with NO comments and asserts `## Comments` is absent from the `user_prompt`. Same shape for `## Labels` when `issue.labels` is empty.
- [ ] A new test in `packages/foreman/tests/test_roles_reviewer.py` for `target == "spec_pr"` seeds an issue with one human comment and asserts `## Comments` + `### @alice` appears in the reviewer's `user_prompt`. NO `## Labels` section.
- [ ] A new test in `packages/foreman/tests/test_roles_reviewer.py` for `target == "impl_pr"` seeds an issue with one human comment AND labels `{"foreman:impl-review", "priority:high"}`, runs `run_reviewer` on an impl PR, and asserts that `## Comments` is absent from `user_prompt`. The fixture issue's `get_comments()` is NEVER called (assert on the call counter).
- [ ] Analogous spec-side and impl-side tests for `Fixer` land in `packages/foreman/tests/test_roles_fixer.py` (one with `target="spec_pr"` asserting `## Comments` appears, one with `target="impl_pr"` asserting `## Comments` is absent AND `issue.get_comments()` was never called).
- [ ] A new test in `packages/foreman/tests/test_roles_worker.py` seeds an issue with one human comment AND labels `{"foreman:plan-approved", "priority:high"}`, runs `run_worker`, and asserts `## Comments` and `## Labels` are both absent from the `user_prompt`. Worker fakes' `get_comments()` is never called.
- [ ] Project-level quality gate: `just check` exits zero. New failures: zero.

## Approach
The change factorizes into three layers, kept thin so the Worker's spec-impl-separation discipline (per the issue's Design principle) is preserved by construction:

**Layer 1 — Data + abstraction** (`git_host.py` + `git_hosts/github.py`). A new `CommentRef` frozen dataclass mirrors `IssueRef`'s shape (frozen, dataclass-style, lives next to its sibling). The provider gets a new abstract `get_issue_comments(repo_slug, issue_number) -> list[CommentRef]`; `GitHubProvider` implements it via PyGithub's `repo.get_issue(N).get_comments()`. **No filtering at the provider layer** — the provider returns raw chronological comments; bot filtering is a role-policy concern and lives one layer up.

The issue's source-file pointer claim that `daemon_host.py` already has `get_issue` is wrong on this repo — `daemon_host.GitHubDaemonHost` does NOT expose `get_issue`; the issue-fetch surface lives on `GitHostProvider` / `GitHubProvider`. Putting `get_issue_comments` on `GitHostProvider` (next to `get_issue`) is the right home and keeps the Planner's existing "Looper pattern" (LLM-agnostic, deterministic ops live in core behind the provider) intact.

**Layer 2 — Helpers** (new `roles/_prompt_helpers.py`). Three small pure functions: `format_comments_section`, `format_labels_section`, `filter_bot_self_comments`. Empty inputs return `""` so role composers can splice unconditionally without an empty-header check. Sorting labels alphabetically is a determinism choice — the LLM doesn't need stable order but tests benefit. **Pattern naming (per `CLAUDE.md` Decision 4):** SRP applies — one tiny module, three formatters with no I/O. The "make the right thing easy" Google principle applies to a future role addition: a hypothetical Reviewer-on-stack-PR or Reviewer-on-docs-PR plugs into the same helpers without reinventing the prompt-section shape.

**Layer 3 — Bot-login derivation** (`identity.py`). The issue specifies `foreman-planner[bot]` / `foreman-reviewer[bot]` / `foreman-fixer[bot]` / `foreman-worker[bot]` as the foreman role-bot logins, citing a (non-existent in this repo) `V4Config.apps`. The actual repo derives App slugs dynamically via `IdentityRegistry._get_app_metadata(role)` (see `identity.py:194-201`) — each project's GitHub Apps could in principle have different slugs. The right surface is therefore a new public method `IdentityRegistry.get_role_bot_logins() -> set[str]` that queries `_get_app_metadata` for each of the four role keys and returns `{f"{meta.slug}[bot]" for meta in metas}`. Existing app-metadata caching (`identity.py:81 self._app_meta_cache`) means the second-and-onward calls are free. Cost on first call: at most three extra `GET /app` HTTP calls (the calling role's metadata is already cached) — negligible compared to a multi-second LLM run.

**Layer 4 — Role wiring**:
- `roles/planner.py` (`_build_user_prompt` + `run_planner`): the composer gains `comments` and `labels` kwargs and splices the helper outputs between `## Body` and the closing instruction line. The dispatch path adds two new pre-LLM calls (`host.get_issue_comments(...)` + `registry.get_role_bot_logins()`) inside the existing wrap so failures fire the foreman#229 runaway-burn defense.
- `roles/reviewer.py` (`_build_user_prompt` + `run_reviewer`): the composer gains a `comments` kwarg. The dispatch path branches **before** the fetch: only `target == "spec_pr"` fetches via `issue.get_comments()` and filters; `target == "impl_pr"` passes `[]`. This is a deliberate gate — branching at the fetch site means Reviewer-on-impl never touches comments at all, which makes the "byte-identical impl prompt" regression test trivially correct by construction rather than by coincidence.
- `roles/fixer.py` (`_build_user_prompt` + `run_fixer`): same shape as the Reviewer. The composer gains `comments`; `run_fixer` branches on `target` before the fetch.
- `roles/worker.py`: unchanged. The regression test in `test_roles_worker.py` proves the user prompt is identical even when the seeded issue would have provided comments and labels.

The fetch+filter call site in Reviewer/Fixer (which already hold a PyGithub `Issue` from `repo.get_issue(...)`) reuses `_prompt_helpers.filter_bot_self_comments` directly — the raw PyGithub comments get walked into `CommentRef` via a small inline loop, then filtered. The Planner goes through `host.get_issue_comments` (which performs the equivalent walk inside the provider) and then filters at the role layer with the same helper. This is the minimum-coupling pattern: the provider abstraction stays Planner-clean; Reviewer/Fixer keep their existing PyGithub-direct shape.

Project conventions followed: PR title `feat(roles): ...` (per `.foreman/INSTRUCTIONS.md` "Use standard conventional-commit types only"; the work adds new behavior — a new role-input data channel — so `feat`, not `refactor`). Subject lowercase. Pattern naming surfaced. Tests-first per `just check` discipline.

## Alternatives considered
- **Hardcode the four foreman role-bot logins as string constants in `_prompt_helpers.py`.** Rejected: `IdentityRegistry` derives App slugs dynamically via `fetch_app_metadata` (`identity.py:194-201`), and a project that registers GitHub Apps with non-default slugs would silently bypass the filter — letting bot self-comments leak back into Planner reruns and reintroducing the issue this ticket exists to fix. The runtime cost of three extra `GET /app` calls per Planner run (cached after first) is negligible.
- **Filter all GitHub Bot accounts (`comment.user.type == "Bot"`) rather than the foreman-role-bot subset.** Rejected: the issue body is explicit — "Filter out the foreman role bots' own comments." Dependabot or release-please bot comments may carry operationally relevant context (security advisories, release-blocker notes) that should reach the Planner. Over-filtering is harder to debug than under-filtering.
- **Put `get_issue_comments` on `daemon_host.GitHubDaemonHost` as the issue body suggests.** Rejected: `daemon_host` is the orchestrator-bot-backed adapter used by the daemon's reconciler for label management + PR merging; it has no role-side consumers today. The Planner already goes through `GitHostProvider` for `get_issue`, so adding `get_issue_comments` there keeps the abstraction whole and means a future non-GitHub provider (the `GitLabProvider` named in `git_host.py:6`) just needs to implement one more method, not two scattered surfaces.
- **Have Reviewer/Fixer go through `GitHostProvider.get_issue_comments` for parity with the Planner.** Rejected: Reviewer and Fixer already use PyGithub directly throughout `run_reviewer` / `run_fixer` (`reviewer.py:528`, `fixer.py:477`); pulling them onto `GitHostProvider` is a larger refactor that the issue body does not request. The existing asymmetry — Planner-via-provider, Reviewer/Fixer-via-PyGithub — is preserved; the shared `filter_bot_self_comments` helper covers the de-duplication concern.
- **Branch on `target` inside `_build_user_prompt` (single composer, target-aware).** Rejected: branching at the composer means `run_reviewer`/`run_fixer` always fetch comments — adding latency + an unnecessary API call on the impl path, AND making the "byte-identical impl prompt" regression test depend on the composer's branch logic rather than on the fetch being skipped. Branching at the dispatch site (before fetch) is cheaper and makes the regression-by-construction argument crisp.
- **Skip the `## Labels` section entirely** (treat it as out of scope alongside Reviewer-on-spec / Fixer-on-spec). Rejected: the issue body explicitly asks for labels on the Planner only, with the rationale that `bug` / `feat` / `epic` may inform the Planner's spec shape. Including it adds three lines of code and one helper, well under the noise floor.

## Open questions
- **`V4Config.apps` is mentioned in the issue body but does not exist in this repo.** The actual config is `foreman.config.AppsConfig` (`config.py:360`), which only stores `*_app_id` and `*_private_key_path` — slugs are not stored at all. The spec resolves this by deriving slugs at runtime via `IdentityRegistry.get_role_bot_logins()`. The Reviewer should sanity-check that the dynamic-lookup approach is acceptable; the alternative (hardcoded slugs) is documented in Alternatives considered.
- **`daemon_host.py` does NOT have `get_issue`** (the issue body asserts it does). The spec routes through `GitHostProvider.get_issue_comments` instead, matching the Planner's existing fetch path. If the Reviewer prefers `daemon_host` placement for some reason not stated in the issue body, the spec can be refactored, but the abstraction layering favors `GitHostProvider`.
- **The CLI symbols named in the issue body (`run_planner_cli`, `run_reviewer_cli`, `run_fixer_cli`) do not exist** — the role entry points are `run_planner` / `run_reviewer` / `run_fixer` themselves, each of which already performs its own issue fetch. The spec wires the comment fetch inside those functions rather than in a non-existent CLI layer; the Worker should treat this as the intended target.

## Out of scope
- Worker, Reviewer-on-impl, Fixer-on-impl behavior. Their prompts must remain byte-identical to current behavior even when comments/labels exist on the issue. The regression tests enforce this; the implementation guarantees it by branching on `target` before the fetch.
- PR review-comment injection. The Fixer-on-impl already consumes PR review comments via its findings-extraction pipeline; that flow is unchanged.
- Comment filtering beyond "exclude foreman role-bot self-comments." Per-author / time-window / linked-issue filters are explicit follow-ups in the issue body.
- Comments on linked or referenced issues. Only the target issue's own comments are fetched.
- Real-time / mid-execution comment injection. Comments are fetched once at role dispatch.
- Updates to the operator-vault `using-foreman-file-ticket` skill. Tracked in the issue body as a follow-up.
- Operator-side `~/.foreman/v4/config.toml` edits. No operator config is required.
- Refactoring Reviewer/Fixer to use `GitHostProvider` for their other GitHub access — preserve existing PyGithub-direct shape outside the new comment fetch.
- Adding pagination handling for issues with hundreds of comments. PyGithub's `PaginatedList` already iterates lazily; the list-comprehension materializes it. Re-evaluate if a real ticket ever has comment-volume issues.
